# 04 — User interface

GTK4 + libadwaita, following GNOME HIG. Not because the target user runs GNOME —
this one runs KDE — but because libadwaita gives us adaptive layout, a
consistent preferences idiom, and dark mode for free, and because boxflat's
users already recognise the shape.

## Principles

- **The device is the source of truth.** Every value shown is read from the base.
  No shadow state, no "apply" button that might be lying. If we can't read it
  back, we don't claim it.
- **Live feedback beside every control.** Changing a curve while watching the
  axis readout move is the entire reason to do this on the desktop instead of in
  a config file.
- **Nothing writes on hover.** Sliders commit on release, not on every frame of
  drag. EEPROM has a write-cycle budget and the serial link is 115200 baud.
- **Missing hardware is a state, not an error.** The base is powered separately
  and is off most of the time. "No base connected — power it on and I'll pick it
  up" is a designed screen.

## Layout

`AdwApplicationWindow` with an `AdwNavigationSplitView`: device list on the left
(usually one item), pages on the right via `AdwViewStack`. Collapses to a single
pane on narrow windows, which also makes it usable on a Steam Deck.

### Pages

**Overview**
Device tile: model, firmware version, serial link, USB path, connection state.
Live 2-axis position dot with the current soft-limit box drawn around it — the
one visual that tells you instantly whether the base is calibrated. Quick
actions: backup config, restore, reload from device.

**Axes**
Per axis (X/roll, Y/pitch): centre, range, deadzone, soft limits, invert.
A **response curve editor** — draggable control points over a live trace of
actual stick position, so you can see where your hand spends its time. Presets:
linear, mild, aggressive, custom. Reset-to-device and reset-to-default on every
control.

**Force Feedback**
Master gain. Spring, damper, friction, inertia. Effect-strength trims where the
protocol exposes them. Below: a read-only panel showing what the *kernel* sees —
which PID effects `hid-pidff` reports on the evdev node, and whether anything
currently holds the device. Nothing else on Linux tells you this, and it's the
first question when someone says "my FFB stopped working".

**Grip**
Detected or manually selected grip, with a rendered button map. Click a button
on the diagram to see its index and name; press it on the stick and it lights
up. Hat configuration. Shift layers. A "copy DCS binding list" action.

**Profiles**
Named profiles with per-sim/per-aircraft notes. Apply, duplicate, export, import.
A diff view before applying — "this changes 6 settings" with the list — because
silently rewriting someone's tuned setup is unforgivable.

**Diagnostics** (hidden unless enabled in preferences)
Live protocol log with decoded frames. A raw command console for development.
Capability dump for bug reports. `confidence` and `safety` shown per setting, so
a user can see exactly which values are well understood and which are inferred.

## Live data

Axis and button state come from **evdev**, read-only, not from the serial
channel. It's faster, it's what the game sees, and it costs the config link
nothing. The serial channel is used only for settings.

Refresh at ~60 Hz for the visualiser, decimated into the UI thread via
`GLib.idle_add`. If the device is in use by a game, we still read fine — evdev
reads don't conflict.

## Error presentation

Three distinct states with three distinct screens, never one generic error:

1. **No device.** Base off or unplugged. Friendly, expected, self-resolving.
2. **Device present but not permitted.** The udev rule is missing. Show the exact
   rule, the exact path, and a copyable command. This will be the single most
   common support issue and deserves a real screen, not a stack trace. Note the
   `70-` prefix requirement (see [`01-architecture.md`](01-architecture.md)).
3. **Device present, unrecognised.** Unknown PID. Show what we can read, offer
   the contribution flow.

## CLI parity

The CLI is not a lesser sibling. Everything the GUI can do, `tux-ffb-cli` can do:

```
tux-ffb-cli list                          # devices found
tux-ffb-cli info                          # model, firmware, capabilities
tux-ffb-cli dump [--json]                 # every readable setting
tux-ffb-cli get  axis.x.range
tux-ffb-cli set  axis.x.range 90
tux-ffb-cli backup  ab9-before.yaml
tux-ffb-cli restore ab9-before.yaml
tux-ffb-cli profile apply dcs-viper.yaml
tux-ffb-cli monitor                       # live axis/button stream
tux-ffb-cli probe --scan-reads            # read-only protocol exploration
```

`--json` on every read command, so this is scriptable from a launcher script
that sets up the stick before DCS starts.
